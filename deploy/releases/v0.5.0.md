# Edge Manager v0.5.0

This release reorganizes deployments around a device workspace and adds a
product release badge with component build details. It also includes the OVH
Managed Kubernetes deployment configuration introduced since v0.4.1.

## Deployment workspace

- Configuration, Setup and Device activity have distinct views. Configuration
  appears first and includes the selected configuration name; workspace buttons
  show a pointer cursor and selected state.
- Device selection supports search and domain/network filters. New devices
  start with a local draft; selecting a device or navigating stages does not
  create a saved configuration.
- Drafts and the current setup stage survive view changes and reloads. Changes
  of device, version or route offer an explicit save/discard choice, and a
  failed save preserves the draft.
- Installation and provisioning show a review of the exact target and
  configuration. Installation requires target-disk acknowledgement. Saving
  configuration and running an operation are separate actions.
- Progress polling continues when its dialog is closed, with access to device
  activity and logs. Layouts support phones, tablets and desktops in English
  and Spanish.

## Product version and diagnostics

- The badge beside Edge Manager opens deployment details with the declared
  product release, frontend/backend package versions, source revisions and
  build times. Development builds show `DEV` and their source commit.
- The dialog identifies differences between declared and actual builds and
  offers copyable diagnostic metadata, including a manual-copy fallback.
- CI and local image builds embed build identity. An authenticated endpoint
  reads a validated deployment manifest; no application secrets or logs are
  included in the diagnostic response.
- Each Kubernetes overlay owns its release declaration. Manifest tooling
  generates the intended component set and can record a read-only snapshot of
  deployed images and readiness. Snapshots are dated evidence; workflow and
  migration targets are not presented as proof of application.
- The versioning contract is documented in backlog decision-036, with the
  operator procedure in `deploy/RELEASE.md`.

## Infrastructure and component versions

- OVH Managed Kubernetes configuration and its Terraform deployment workflow
  are included, along with the migration runbooks from the local kind setup
  (task-142).
- Product release: `v0.5.0`; frontend: `0.11.0`; backend: `1.1.0`. Component
  versions remain independent of the product release.
- No new database migration or Node dependency is required by the workspace
  and version-diagnostics changes.

## Upgrade notes

Build frontend and backend images from this tag, verify their provenance, pin
their digests, and generate the intended overlay's release manifest before
rollout. The checked-in manifests initially contain `null`; the badge falls
back to a build identifier until a release is declared. Older backends remain
usable but cannot supply deployment details.

Deploy OVH resources through their Terraform owner. Publishing this release
does not deploy the platform or perform gateway installation/provisioning.

## Validation and known limitations

- Frontend: 45 unit tests passed. Backend: 56 unit tests passed. Build metadata:
  3 tests passed. Release manifest tooling: 4 tests passed.
- Frontend/backend builds, changed-source format checks, workspace typecheck
  and all three Kubernetes overlay renders passed. The deployment workspace
  browser spec still has 8 pre-existing lint errors (unchanged from its
  refactor commit).
- All 14 isolated browser scenarios of the deployment workspace passed in
  Chromium, including the version-badge scenario (responsive deployment
  details and manual copying).
- Direct application TypeScript checking still reports 119 pre-existing
  diagnostics, matching the pre-release-feature baseline by file and code.
  The standard workspace typecheck does not expose those application errors.
- Concurrent operators can still race when allocating configuration versions;
  duplicate-launch prevention applies to the current workspace. Cross-session
  locking and backend idempotency remain separate work.

Changes are relative to `v0.4.1`.
