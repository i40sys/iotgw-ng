## Context

After decision-033, three weaknesses of the device API remain (tasks 133-135):

- gateways and live images call `vpn` / `ssh-ca` over **plain HTTP**
  (`http://10.2.0.47:8000`, Kong's NodePort);
- the **WireGuard private key** is generated by Netmaker, stored in
  `devices.private_key` and sent to the gateway (sealed since decision-033);
- the legacy code-encrypted `vpn` reply and `devices.totp_counter` still exist
  for live images deployed before v0.3.0.

Facts: from the gateway LAN, 10.2.0.47 exposes the kind ingress on **443**
(`*.wsl.ymbihq.local` names resolve to a WSL-internal address, so gateways use the
IP); Netmaker v1.0 ext clients carry a settable `publickey`; the live image is
served from `y0:/opt/stacks/netbootxyz/assets/iotgw-live`.

## Decision

### 1. TLS for the device API, CA pinned on the gateway

- A dedicated **device-API CA** (EC P-256, 10 y) issues a server certificate for
  `IP:10.2.0.47` + `DNS:api.wsl.ymbihq.local` (825 d). Keys live in SOPS
  (`secrets/device-api-tls.enc.yaml`); the CA certificate is public and committed
  (`live-image/overlay/etc/iotgw/api-ca.pem`).
- ingress-nginx serves it as its **default certificate** (requests to the bare
  IP carry no SNI) and a host-less Ingress routes only
  `/functions/v1/vpn` and `/functions/v1/ssh-ca` to Kong.
- Gateways **pin** the CA: when `api_base` is `https://…` and
  `/etc/iotgw/api-ca.pem` exists, the agent trusts only that CA.
- **Upgrade rule:** when that pinned CA is present and the configured `api_base`
  is `http://host[:port]`, the client uses `https://host` instead — never falling
  back to HTTP. The iPXE menu that passes `iotgw_api=http://10.2.0.47:8000` lives
  on a host outside this repo, so the live image (which ships the CA in its
  overlay) upgrades by itself and records the **effective** https `api_base`,
  which the install copies into the new OS together with the CA.
- Plain HTTP stays available in-cluster (Kong service) — clients configured with
  https never downgrade.

### 2. The gateway holds its WireGuard private key

- The gateway generates its WireGuard key pair and sends only
  `wg_public_key` in the (code-authenticated, sealed) `vpn` request. An installed
  gateway **reuses** its current key (from `network.wg0.private_key`) so a refresh
  normally changes nothing on Netmaker and a rollback stays valid; the live image
  generates one per boot (the install carries it into the new OS).
- `vpn`: if `wg_public_key` differs from the device's, it updates the Netmaker
  ext client's `publickey` (`PUT /api/extclients/{network}/{clientid}`), stores
  the new public key and **clears `devices.private_key`**. The returned config has
  **no `PrivateKey` line** — the gateway inserts its own.
- A device whose private key is gateway-held (`private_key` null) is refused a
  keyless legacy request (409).

### 3. Legacy removal

After the live image on y0 runs the new agent: the `vpn` function no longer serves
the code-encrypted reply (`reply_key` required) and `devices.totp_counter` is
dropped.

## Consequences

- No private key is transmitted or stored server-side for gateways on the new
  agent; the device API is encrypted in transit and authenticated by a pinned CA.
- Rotating the gateway key is explicit (`iotgw vpn refresh -otp CODE -rotate-key`)
  or implicit on a live-image boot.
- The CA/cert pair must be renewed before expiry (the cert is 825 d) — tracked in
  the runbook in `secrets/README.md`.
